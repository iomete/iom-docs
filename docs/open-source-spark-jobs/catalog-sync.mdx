A searchable data catalog is only useful if it stays in sync with what's in your warehouse. The **Data Catalog Sync Job** scans every catalog in your IOMETE environment and indexes the tables it finds. Indexed tables appear on the **Data Catalog** page, where you can add documentation, assign owners, define classifications, and set maintenance properties.

- **Version:** see the [Marketplace Jobs release notes](../deployment/on-prem/release-notes/marketplace-jobs.md) for the latest version (requires IOMETE `3.16.x` or later)
- **Source:** [View on GitHub](https://github.com/iomete/iomete-marketplace-jobs/tree/main/iomete-catalog-sync)

## How It Works

Once deployed, the job runs on its own. It fires on a schedule (hourly by default), scans every catalog in your environment (or only the ones in your [inclusion list](#inclusion-rules)), and indexes the tables it finds. Anything matching an [exclusion rule](#exclusion-rules) is skipped.

You can change the schedule or trigger a run manually at any time.

## Running the Job

The schedule handles most cases. If you need a fresh index right now (say, after creating a batch of new tables), open the job and click <FlexButton label='Run' primary><Play size={12} weight="fill" /></FlexButton>.

## Deleted Tables

Dropping a table doesn't erase its history from the catalog. That history is useful when you need to know what existed before and when it disappeared. When a table is dropped from a source catalog, the sync job marks it as **deleted** and hides it from the default view instead of removing the record.

To review what was removed and when, use the **Deleted** toggle in the Data Catalog UI.

<Img
  src="/img/spark-job/marketplace/catalog-sync/data-catalog-deleted.png"
  alt="Data Catalog deleted tables view"
/>

:::note
Deleted entries are kept indefinitely for now. Automatic cleanup of old deleted entries is planned for a future release.
:::

## Inclusion Rules

:::info
Inclusion rules require catalog-sync `5.3.0` or later.
:::

To sync only a few catalogs, list them instead of excluding everything else. Catalogs created later aren't synced unless you add them to the list.

```json
{
  "inclusion_rules": {
    "catalogs": {
      "names": ["hot_catalog"]
    }
  }
}
```

- Leave `inclusion_rules` out, or use an empty `names` list, to sync every catalog.
- Names match exactly, case included.
- In a private domain, names are checked only against catalogs the domain owns and whose settings were included when the job launched. An owned catalog missing from those launch settings is treated as an unknown name.

### How Inclusion and Exclusion Combine

1. The inclusion list narrows the catalogs to sync.
2. Every [exclusion rule](#exclusion-rules) still applies to what's left: `catalogs.names`, `catalogs.filter_by_properties`, and `default_rule`.
3. Exclusion always wins. A catalog that is in the inclusion list and matches any exclusion rule isn't synced, and the job logs a warning naming the rule.

For example, outside private domains, an included catalog with `iomete.governance.index=false` is never synced, because the default rule excludes it.

:::caution Private domains
In a private domain, the job doesn't receive catalog properties, so catalog-level property rules (`catalogs.filter_by_properties`, and `default_rule` at catalog level) never match. An included catalog with `iomete.governance.index=false` **is** synced there, and no warning is logged. To skip a catalog in a private domain, list it in `exclusion_rules.catalogs.names`. Schema and table property rules still work.
:::

### Catalogs the Job Can't Sync

An included catalog can't be synced if its name matches no catalog or, in a private domain, if the domain doesn't own it or the job wasn't launched with its settings.

- If some included catalogs can't be synced, the job logs a warning listing the catalogs it can sync, and syncs the rest.
- If **none** of them can be synced, the run fails before syncing anything. This catches a misspelled name that would otherwise sync nothing on every run.

### Removing a Catalog from the Sync

Taking a catalog out of the inclusion list, or adding it to the exclusion list, doesn't remove what was already synced for it. The job only marks tables as deleted in catalogs it visits, so a catalog it no longer visits keeps its last synced metadata, and that metadata stays searchable.

### Syncing One Catalog More Often

A common setup is a frequent job for one busy catalog next to the regular hourly job for everything else:

- **Hourly job:** syncs all catalogs. Add `hot_catalog` to its `exclusion_rules.catalogs.names`.
- **15-minute job:** `"inclusion_rules": {"catalogs": {"names": ["hot_catalog"]}}`, schedule `*/15 * * * *`.

Excluding `hot_catalog` from the hourly job matters. Concurrency `Forbid` only stops a job from overlapping with itself, so without the exclusion both jobs can index `hot_catalog` at the same time.

## Exclusion Rules

Not every catalog needs to be indexed. For example, you may want to skip:

- An external catalog (e.g., Oracle) with millions of tables that would clutter search results
- Catalogs or schemas containing sensitive data that shouldn't appear in the Data Catalog
- Personal or sandbox environments used for development

Exclusion rules let you skip specific catalogs, namespaces (schemas/databases), or tables during sync.

### Default Rule

For a single rule that covers everything, start here. The default rule applies at **all levels**: catalogs, schemas, and tables. Any asset with a matching property is excluded from indexing.

```json
{
  "exclusion_rules": {
    "default_rule": {
      "filter_by_properties": {
        "iomete.governance.index": "false"
      }
    }
  }
}
```

With this rule in place, setting `iomete.governance.index=false` on any catalog, schema, or table excludes it from the sync. One rule, applied wherever you need it via properties.

### Excluding Catalogs

For catalog-level control, exclude catalogs **by name**, **by property**, or both.

#### By Name

List catalog names directly. These catalogs are always skipped, regardless of their properties.

```json
{
  "exclusion_rules": {
    "catalogs": {
      "names": ["sandbox_dev", "legacy_warehouse", "user_personal_spaces"]
    }
  }
}
```

#### By Property

Set `iomete.governance.index` to `false` on the catalog in the **Admin Portal** when you create or edit it.

<Img
  src="/img/spark-job/marketplace/catalog-sync/exclude-catalog.png"
  alt="Setting iomete.governance.index property on a catalog in the Admin Portal"
/>

Then add the matching filter:

```json
{
  "exclusion_rules": {
    "catalogs": {
      "filter_by_properties": {
        "iomete.governance.index": "false"
      }
    }
  }
}
```

#### Combining Both

Use names and properties together. A catalog is excluded if it matches **either** condition.

```json
{
  "exclusion_rules": {
    "catalogs": {
      "names": ["sandbox_dev", "legacy_warehouse"],
      "filter_by_properties": {
        "iomete.governance.index": "false"
      }
    }
  }
}
```

### Excluding Namespaces (Schemas/Databases)

To keep a catalog in the index but skip a few schemas inside it, use namespace exclusion. It's property-based. Set the property in SQL to mark a namespace for exclusion:

```sql
ALTER DATABASE my_catalog.my_schema SET DBPROPERTIES ('iomete.governance.index' = 'false');
```

Verify the property:

```sql
DESCRIBE DATABASE EXTENDED my_catalog.my_schema;
```

To re-enable indexing later, flip the property back:

```sql
ALTER DATABASE my_catalog.my_schema SET DBPROPERTIES ('iomete.governance.index' = 'true');
```

Then add the exclusion rule:

```json
{
  "exclusion_rules": {
    "schemas": {
      "filter_by_properties": {
        "iomete.governance.index": "false"
      }
    }
  }
}
```

### Excluding Tables

Tables work the same way as namespaces. Set a property on the table, then define the matching rule.

```sql
ALTER TABLE my_catalog.my_schema.my_table SET TBLPROPERTIES ('iomete.governance.index' = 'false');
```

Verify the property:

```sql
SHOW TBLPROPERTIES my_catalog.my_schema.my_table;
```

To remove the property later:

```sql
ALTER TABLE my_catalog.my_schema.my_table UNSET TBLPROPERTIES ('iomete.governance.index');
```

Then add the exclusion rule:

```json
{
  "exclusion_rules": {
    "tables": {
      "filter_by_properties": {
        "iomete.governance.index": "false"
      }
    }
  }
}
```

#### Multiple Properties (OR Logic)

When a table exclusion rule lists multiple properties, a table is excluded if **any** of them match.

```json
{
  "exclusion_rules": {
    "tables": {
      "filter_by_properties": {
        "iomete.governance.index": "false",
        "hidden": "true"
      }
    }
  }
}
```

A table is excluded if `iomete.governance.index` is `false` **or** `hidden` is `true`. It doesn't need to match both.

### Full Example

A complete configuration that uses every exclusion level:

```json
{
  "exclusion_rules": {
    "catalogs": {
      "names": ["sandbox_dev", "legacy_warehouse", "user_personal_spaces"],
      "filter_by_properties": {
        "iomete.governance.index": "false"
      }
    },
    "schemas": {
      "filter_by_properties": {
        "iomete.governance.index": "false"
      }
    },
    "tables": {
      "filter_by_properties": {
        "iomete.governance.index": "false",
        "hidden": "true"
      }
    },
    "default_rule": {
      "filter_by_properties": {
        "iomete.governance.index": "false"
      }
    }
  }
}
```

## Config Errors

From version `5.3.0`, the run fails instead of falling back to the defaults when `/etc/configs/application.json` exists but can't be parsed. Common causes:

- The file isn't valid JSON, for example because it contains `//` comments.
- A rule has an unknown key, such as `"schemas": {"names": [...]}` or camelCase `filterByProperties` instead of `filter_by_properties`.

Unknown top-level keys are ignored. An empty file is treated like a missing one.

If your job started failing after an upgrade, check the driver logs for `Failed to parse config file` and fix the file.
