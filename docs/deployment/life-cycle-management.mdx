Upgrade the Helm release that owns the services you want to change. Keep its chart, namespace and values together: a control plane and an additional data plane use different charts.

## Choosing the Release {#installation}

| Installation | Chart | What the release manages |
|---|---|---|
| Control plane with its default data plane | `iomete/iomete-data-plane-enterprise` | Console, APIs and default-plane runtime services. |
| Control plane with `defaultDataPlane.enabled: false` | `iomete/iomete-data-plane-enterprise` | Control-plane services; workload data planes are installed separately. |
| Additional data plane | `iomete/iomete-lakehouse-runtime` | Runtime services and configured workload namespaces; no separate console. |

For a new installation, use the [on-premises installation guide](./on-prem/install.md). For another workload namespace on an existing plane, use [Adding a Kubernetes Namespace](./connect-namespace.md). Adding a namespace does not require installing another release.

### Identifying an Existing Release {#installation-example}

Check the Kubernetes context, then locate the release:

```shell
kubectl config current-context
helm list --all-namespaces
```

The `NAME`, `NAMESPACE` and `CHART` columns identify the release. The chart version is part of `CHART`; it is not necessarily the same as `APP VERSION`. For a data plane in another Kubernetes cluster, switch to that cluster before running Helm or `kubectl`.

The examples below use the control-plane release from the installation guide. For an additional data plane, replace **all three** variables with its existing release, service namespace and runtime chart:

```shell
RELEASE="data-plane"
NAMESPACE="iomete-system"
CHART="iomete/iomete-data-plane-enterprise"
```

Do not change an existing release from the enterprise chart to the runtime chart or the other way around.

## Preparing an Upgrade {#upgrades}

### Selecting a Version {#semantic-versioning}

Read the target version's [release notes](./on-prem/release-notes/index.md) and upgrade requirements. Confirm the supported combination of control-plane, data-plane and Spark image versions, including any required intermediate upgrade. A version number alone does not establish database downgrade compatibility.

```shell
TARGET_VERSION="<approved-chart-version>"
helm repo update
helm show values "$CHART" --version "$TARGET_VERSION" > target-defaults.yaml
```

### Planning the Maintenance Window {#upgrade-notification-and-support}

Back up PostgreSQL and retain the corresponding storage, configuration and Secrets needed for recovery. Check the release-specific migration and recovery procedure before starting. A Helm revision does not back up your databases, object storage or externally managed Secrets.

Account for active jobs, queries and notebooks when scheduling the change. Restarting services or changing runtime versions can interrupt connections; a successful rolling deployment does not guarantee uninterrupted queries. For storage changes, follow the separate [storage migration procedure](./storage-migration.md).

### Saving and Reviewing Values {#upgrade-process}

Start with the complete values file used for the existing release. If you need to recover its submitted overrides, save them privately:

```shell
umask 077
mkdir -p release-backup
helm get values "$RELEASE" --namespace "$NAMESPACE" --output yaml \
  > release-backup/values-before.yaml
helm get values "$RELEASE" --namespace "$NAMESPACE" --all --output yaml \
  > release-backup/effective-values-before.yaml
helm history "$RELEASE" --namespace "$NAMESPACE" \
  > release-backup/history-before.txt
```

The `--all` file records the effective old defaults for comparison. Do not blindly use every old default as an override for a new version. Merge the submitted overrides and any intentional changes into `values-next.yaml`, using `target-defaults.yaml` and the release notes to resolve renamed or removed settings.

Preserve these settings unless you are intentionally changing them:

- The **complete `namespaces` list**, including every namespace already managed by this plane. Helm replaces lists; a file containing only a newly added namespace can remove the existing entries.
- Database, storage, registry, truststore and Secret references, plus service-account and webhook ownership settings.
- Data-plane identity and addresses under `multiCluster`. These are not ordinary version-upgrade settings; registered addresses may remain pinned after a Helm change.
- Resource settings, scheduling constraints and deliberate image overrides. Review overrides against the target version so an old image does not remain pinned accidentally.

If the target release changes Spark Operator CRDs, coordinate their update before the service upgrade. CRDs are shared across releases in the same cluster and Helm does not update them during `helm upgrade`. See [Upgrading the CRDs](./on-prem/install.md#upgrading-the-crds).

## Applying and Verifying the Upgrade {#upgrade-example}

Use `helm upgrade` for the existing release. The explicit chart version and complete values file make the intended change reviewable:

```shell
helm upgrade "$RELEASE" "$CHART" \
  --namespace "$NAMESPACE" \
  --version "$TARGET_VERSION" \
  --reset-values --values values-next.yaml \
  --wait --timeout 15m
```

`--reset-values` starts with the target chart's defaults, then applies `values-next.yaml`. It is appropriate here because that file includes all overrides you intend to retain. Do not substitute a small change-only file. Keep the original chart family and release name; `--install` is unnecessary for an upgrade and can hide a mistyped release name by creating a new installation.

Check the result:

```shell
helm status "$RELEASE" --namespace "$NAMESPACE"
kubectl get deployments,statefulsets,pods --namespace "$NAMESPACE"
kubectl get events --namespace "$NAMESPACE" --sort-by=.lastTimestamp
```

Verify both Kubernetes readiness and product behavior:

1. Confirm the expected replicas are ready in the service namespace and every managed workload namespace.
2. Open the control-plane console and confirm the affected data plane is connected.
3. Check that existing namespace assignments remain available. If you added a namespace, complete the [namespace verification steps](./connect-namespace.md).
4. Run `SELECT 1` on a compute in the affected data plane and check the workload types you use, such as scheduled jobs or Jupyter containers.

A ready agent proves only that its pod is running. It does not prove that the control plane can authenticate cross-plane requests or query a remote compute through TLS and HTTP/2.

## Recovering From a Failed Upgrade {#rollback-process}

Inspect the failure before choosing a recovery action:

```shell
helm history "$RELEASE" --namespace "$NAMESPACE"
kubectl get jobs,pods --namespace "$NAMESPACE"
kubectl describe pod <failing-pod> --namespace "$NAMESPACE"
kubectl logs <failing-pod> --namespace "$NAMESPACE" --all-containers --tail=100
```

Initialization hooks may already have changed database schemas or generated configuration before the upgrade fails. `helm rollback` restores a release's Kubernetes manifests; it does not reverse those changes. In particular, the enterprise chart writes its saved values Secret through pre-install and pre-upgrade hooks, which are not rollback hooks. A blind rollback can leave services and saved configuration on different versions.

### Restoring a Known Configuration {#rollback-example}

If the previous chart is compatible with the current database state and the release-specific recovery procedure permits it, reapply that chart with the complete saved values. This runs the normal upgrade hooks:

```shell
PREVIOUS_VERSION="<approved-recovery-chart-version>"
helm upgrade "$RELEASE" "$CHART" \
  --namespace "$NAMESPACE" \
  --version "$PREVIOUS_VERSION" \
  --reset-values --values release-backup/values-before.yaml \
  --wait --timeout 15m
```

If database changes are not backward compatible, use the agreed database and storage restoration procedure instead. Do not attempt the command above to test whether a downgrade works. After recovery, repeat the readiness and product checks and follow any required service restarts in the release-specific instructions. For stale default-plane namespace configuration, see [namespace troubleshooting](./connect-namespace.md).

## Monitoring and Management

Monitor the Kubernetes services and the workloads users run. Check pod restarts, pending pods, failed initialization Jobs, operator errors and available capacity in each managed namespace. If you use Prometheus, Grafana or Loki, maintain their installation and retention policies separately; the IOMETE Helm release is not a backup for those systems.

## Planning Recovery and Availability {#high-availability--disaster-recovery}

A recovery plan includes PostgreSQL, object storage, required Secrets, Helm values and ingress/DNS configuration. Test restoring them together. Additional replicas help only when the service supports them and replicas can run on healthy nodes; they do not replace database or storage backups.

Do not start a second control plane against the same production databases as an improvised failover procedure. Plan the supported topology, credentials and write ownership before bringing up a standby environment.
